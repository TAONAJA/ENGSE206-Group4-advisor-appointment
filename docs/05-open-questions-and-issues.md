## 2. Issues / Holds (ประเด็นที่ต้องชะลอการพัฒนาไว้ก่อน)

| Issue ID | เรื่องที่ต้อง Hold | เหตุผลที่ต้อง Hold | สิ่งที่ต้องเก็บหลักฐานเพิ่ม |
|---|---|---|---|
| **ISSUE-ADV-01** | การเชื่อมต่อตารางเวลากับ Google Calendar ภายนอกแบบอัตโนมัติ (Two-way Sync) | ติดข้อจำกัดด้าน Data Privacy และ IT Policy สถาบัน (เสี่ยงข้อมูลนัดหมายรั่วไหล) | นโยบายการใช้ OAuth/API ของมหาวิทยาลัย และเอกสารอนุมัติจาก IT Admin |
| **ISSUE-ADV-02** | การส่งแจ้งเตือนผ่าน LINE Notify / LINE Official Account หรือ Push Notification | มีค่าใช้จ่ายภายนอกและความซับซ้อน API เกินขอบเขตโครงงาน (Out of Scope) | นโยบายงบประมาณระบบสารสนเทศสถาบัน |
| **ISSUE-ADV-03** | กฎการลงโทษกรณีนักศึกษาไม่มาตามนัด (No-show Penalty Rule) หรือการตัดสิทธิ์จองคิว | ยังไม่มีเอกสารนโยบายอย่างเป็นทางการจากภาควิชารองรับ ห้ามคิดกฎเอง | เอกสารประกาศนโยบายการนัดหมายจากภาควิชา |
| **ISSUE-ADV-04** | การอนุมัติคำขอนัดหมายแบบอัตโนมัติ (Auto-approval System) | อาจารย์ต้องการตรวจสอบวัตถุประสงค์และเตรียมตัวก่อนเข้าพบทุกครั้ง | เอกสารยืนยันเกณฑ์การเข้าพบออโต้ (หากมีในอนาคต) |

## 3. Follow-up Plan (แผนการดำเนินการติดตามข้อมูล)

| Action | Output ที่ต้องได้ | วิธีนำไปใช้ต่อใน Week 06 |
|---|---|---|
| สัมภาษณ์อาจารย์และเจ้าหน้าที่ภาควิชาเพิ่ม (10-15 นาที) | Required Fields ขั้นต่ำ และข้อยกเว้นกฎ 24 ชม. | นำไปเขียน Use Case Precondition, Alternate Flow และ Acceptance Criteria (Given-When-Then) |
| ประสานงานกับ IT Admin เรื่อง SSO & Role Matrix | ตาราง Role & Permission Matrix ที่ชัดเจน | นำไปทำ Security Constraint และ Access Control Rule |
| รวบรวมฟอร์มรายงานสถิติเดิมของภาควิชา (ถ้ามี) | ข้อกำหนดฟิลด์รายงานภาพรวม | นำไปเขียน Reporting Use Case Specification |
| บันทึกประเด็น No-show และ Google Calendar เป็น Issue | บันทึกข้อจำกัด (Limitation Record) | จัดเก็บไว้ในเอกสาร ไม่นำไปออกแบบหรือเขียน Code |
