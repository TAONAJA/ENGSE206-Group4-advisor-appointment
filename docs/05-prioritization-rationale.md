# 05 — Prioritization Rationale: Advisor Appointment System

> ไฟล์นี้อธิบาย “ทำไม” requirement แต่ละข้อของระบบนัดหมายอาจารย์ที่ปรึกษาจึงได้ priority ตามที่กำหนด เพื่อแสดงเหตุผลเชิงวิศวกรรมความต้องการ (Requirements Engineering) ที่วัดจาก Value, Risk, Urgency และ Dependency

## 1. หลักคิดในการจัดลำดับความสำคัญ (Prioritization Principles)

ทีมใช้ 4 คำถามวิเคราะห์ร่วมกับทุก Requirement Candidates (RC) และ Evidence Log:

1. **Value:** นักศึกษา อาจารย์ หรือภาควิชาได้ประโยชน์โดยตรงในการแก้ปัญหานัดหมาย/เดินเก้อ/ตอบแชทซ้ำหรือไม่
2. **Risk:** ถ้าไม่ทำ requirement นี้ จะเกิดปัญหานัดซ้อน (Overlapping), นัดกะทันหัน, ลิบล่วงหน้า หรือข้อมูลส่วนบุคคลรั่วไหลหรือไม่
3. **Urgency:** ต้องใช้ใน Core Workflow รุ่นแรก (ค้นหาเวลา -> สร้างคำขอ -> อนุมัติ -> แจ้งเตือน) หรือยังรอได้
4. **Dependency:** ต้องรอนโยบายภาควิชา (No-show/Cancellation), IT Policy (SSO/Data Privacy) หรือ Role & Permission Matrix ก่อนหรือไม่

## 3. สิ่งที่ยังไม่ได้เลือกเป็น Requirement ทันที (Explicitly Not Chosen Requirements)

| สิ่งที่พบใน Week 04 | เหตุผลที่ยังไม่กำหนดเป็น Requirement ในเฟสนี้ |
|---|---|
| การเชื่อมต่อ Google Calendar แบบ Two-way Sync | ขัดต่อหลัก Data Privacy และนโยบายความปลอดภัย IT สถาบัน (ให้ใช้ระบบปฏิทินภายในจำลองก่อน) |
| การส่งข้อความแจ้งเตือนผ่าน LINE Notify / LINE OA | มีค่าใช้จ่าย API สื่อสารภายนอก และเกินขอบเขตโครงการ (Out of Scope) |
| การสร้างลิงก์ประชุม Zoom / MS Teams อัตโนมัติ | มีความซับซ้อนในการเชื่อมต่อ API มหาวิทยาลัย ให้ใช้วิธีแนบลิงก์ Manual ในระบบแทน |
| การอนุมัติคำขอนัดหมายแบบอัตโนมัติ (Auto-approval) | อาจารย์ต้องการกรอกและตรวจสอบวัตถุประสงค์การเข้าพบด้วยตนเองทุกครั้งเพื่อจัดสรรเวลา |
| บทลงโทษกรณี No-show หรือการตัดสิทธิ์การจองคิว | ยังไม่มีเอกสารนโยบายรองรับอย่างเป็นทางการจากภาควิชา จึงยังไม่สร้าง Business Rule สมมติขึ้นเอง |

## 4. บทเรียนสำคัญสำหรับทีม (Key Takeaways)

- **Priority สูงไม่ได้แปลว่ารายละเอียดครบแล้ว:** เช่น `FR-ADV-02` (ฟอร์มขอเข้าพบ) เป็น Must แต่ยังมีสถานะเป็น `Needs Follow-up` เพราะต้องรอสรุป Required Fields
- **ข้อกังวลด้านเทคนิคต้องไม่ถูกดันเป็น Requirement:** ประเด็นอย่าง Google Calendar หรือ LINE Notify แม้ผู้ใช้จะชอบ แต่เมื่อติดข้อจำกัดด้าน Security/Cost ต้องกล้าจัดเป็น `Hold / Won't yet`
- **ไม่สร้าง Rule เองโดยไม่มี Evidence:** หากยังไม่มีกฎ No-show หรือ Penalty จากภาควิชา ต้องถือเป็น Issue ไว้ Follow-up ไม่ใช่คิดกฎลงโทษขึ้นมาเอง
