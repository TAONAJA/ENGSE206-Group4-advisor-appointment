## ส่วนที่ 1 — Core Twist: Accessibility + Offline (บังคับ)

### 1.1 Frame และ Scope ที่เปลี่ยนไปจาก Twist
> เหตุการณ์ใหม่กระทบขอบเขตเดิมอย่างไร อะไรเข้า/ออก scope

- **In scope (เพิ่ม):**
  1. ทำระบบนัดหมายอาจารย์สำหรับผู้พิการทางสายตาสัมผัสด้วยเสียง
  2. การทำควบคุมด้วยแป้นสัมผัส
  3. ปรับความคมชัดของอักษร ตามมาตรฐาน WCAG 2.1
  4. การดูข้อมูลร่างแบบออฟไลน์ internet หลุดชั่วคราว
- **Out of scope (ยังไม่ทำ):**
  1. ระบบ AI แปลงเสียงอักษรเบรลล
  2. ระบบนำทางในอาคาร
  3. ระบบพบอาจารย์ออนไลน์ในตัว

### 1.2 Stakeholder ที่เพิ่ม/เปลี่ยน
| รหัส | บทบาท | ความต้องการ/ข้อกังวลจาก twist นี้ |
|---|---|---|

| ST-2 |เจ้าหน้าที่ดูแลคนพิการ |สำหรับผู้พิการจะสามารถนัดหมายอาจารย์ได้หรือไม่  |
| ST-3 |ผู้ดูเเลระบบ |ต้องการตรวจสอบข้อมูลนัดหมาย  |

### 1.4 Requirement Backlog (Core)
> อย่างน้อย 4 ข้อ ต้องมี NFR/Constraint ด้าน accessibility และ offline

| REQ-ID | Requirement Statement | Type (FR/NFR/Constraint/Issue) | Priority (MoSCoW) | Trace (E-ID) | เหตุผล priority |
|---|---|---|---|---|---|
| R-1 | ระบบต้องออกแบบ UI และโครงสร้าง DOM ให้รองรับมาตรฐาน WCAG 2.1 Level AA โดยสามารถใช้งานผ่าน Keyboard Navigation และ Screen Reader (เช่น VoiceOver, NVDA) ได้สมบูรณ์พร้อมใส่ ARIA Labels | NFR | Must have | E-01 | เป็นข้อกำหนดหลักของสถานการณ์ใหม่ (Accessibility) เพื่อให้ผู้พิการทางสายตาใช้งานได้จริง |
| R-2 | ระบบต้องรองรับการบันทึกข้อมูลตารางนัดหมายที่ยืนยันแล้วลงใน Local Storage / IndexedDB เพื่อให้เปิดดูข้อมูลแบบออฟไลน์ได้เมื่อสัญญาณอินเทอร์เน็ตหลุด | FR | Must have | E-02 | เป็นฟังก์ชันสำคัญเพื่อป้องกันผู้ใช้เดินทางมาเสียเที่ยวเมื่อไม่มีสัญญาณอินเทอร์เน็ต |
| R-3 | ระบบต้องรองรับการบันทึกร่างคำขอนัดหมาย (Offline Draft) และส่งเข้าคิวซิงก์ข้อมูลไม่อัตโนมัติ (Background Sync) เมื่อเชื่อมต่ออินเทอร์เน็ตอีกครั้ง | FR | Should have | E-02 | ป้องกันข้อมูลวัตถุประสงค์ที่พิมพ์ค้างไว้สูญหายระหว่างอยู่ในจุดอับสัญญาณ |
| R-4 | หน้าจอแสดงผลและข้อความแจ้งเตือนสถานะการทำรายการ ต้องใช้ HTML Live Regions (aria-live="polite") เพื่อให้ Screen Reader ส่งเสียงอ่านยืนยันผลแก่ผู้ใช้ทันที | NFR | Should have | E-03 | เพิ่มความมั่นใจและประสบการณ์การใช้งานที่ถูกต้องสำหรับผู้ใช้ Screen Reader |
| R-5 | การพัฒนาระบบ Accessibility และ Offline ทั้งหมด ต้องเสร็จสิ้นภายใต้งบประมาณและกำหนดเวลาเดิม โดยเน้นใช้ Semantic HTML และ Progressive Web App (PWA) | Constraint | Must have | สถานการณ์ | เป็นข้อจำกัดตรงตามคำสั่งและเงื่อนไขของผู้บริหาร |

### 1.5 Issue / สิ่งที่ยังไม่ยืนยัน
> รวมข้อมูลที่ AI "แต่ง" ให้ ที่กลุ่มตัดสินใจไม่เชื่อ

- ISSUE-1: AI อ้างว่าระบบ Offline Sync ต้องใช้โปรโตคอลความปลอดภัยระดับทหาร
กลุ่มไม่เชื่อ เพราะเป็นการระบุข้อกำหนดที่เกินความจำเป็นสำหรับระบบนัดหมาย
- ISSUE-2: AI เสนอให้สร้างเอนจิน AI ในตัวระบบเพื่อแปลงเอกสารแนบ PDF เป็นไฟล์เสียงและอักษรเบรลล์แบบออฟไลน์
กลุ่มไม่เชื่อ เพราะมีความซับซ้อนเกินจำเป็นและกระทบต่อข้อจำกัดด้านงบประมาณ/เวลาเดิม

## ส่วนที่ 2 — Mini Twist (เลือก 1: A หรือ B)

### 2.1 สถานการณ์ที่เลือกและผลกระทบ
> ผู้บริหารประกาศแต่งตั้ง "ศูนย์ส่งเสริมและพัฒนาคุณภาพชีวิตนักศึกษาพิการ (DSO)" เข้ามาเป็น Stakeholder ใหม่ในฐานะผู้ตรวจสอบมาตรฐานระบบ (Compliance & Audit Stakeholder)

ผลกระทบ: ทำให้ระบบต้องเพิ่มฟีเจอร์การรายงานผลการตวจสอบ ด้าน
การเข้าถึงข้อมูล และเพิ่มขั้นตอนการทดสอบความเท่าเทียมในการเข้าถึง ก่อนเปิดใช้งานจริง โดยต้องบริหารจัดการภายใต้ข้อจำกัดด้านงบประมาณและกำหนดเวลาเดิม

### 2.2 Requirement / Decision ใหม่ (อย่างน้อย 2)
| ID | Requirement / Decision | เหตุผล | Trace |
|---|---|---|---|
| M-1 | เพิ่มหน้าแดชบอร์ดสรุปสถิติ Accessibility Logs และรองรับการทำ Audit Trail สำหรับเจ้าหน้าที่ศูนย์ DSO เข้ามาตรวจสอบการเข้าถึงระบบ | เพื่อตอบสนองความต้องการของผู้ตรวจสอบมาตรฐาน DSO ในการตรวจสอบและรับประกันความเท่าเทียมในการเข้าถึงบริการของนักศึกษาพิการ | Stakeholder DSO (ST-05) |
| M-2 | ตัดสินใจเลือกใช้เทคโนโลยี Progressive Web App (PWA) ร่วมกับ Accessible Rich Internet Applications (ARIA) Standard ในการพัฒนา | เป็นเทคโนโลยีมาตรฐานเว็บที่ไม่เสียค่าลิขสิทธิ์เพิ่มเติม รองรับทั้งการทำงานออฟไลน์และ Accessibility พร้อมกันภายใต้ข้อจำกัดด้านงบประมาณและเวลาเดิม | Constraint (R-5) |
